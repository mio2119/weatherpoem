## 1. 要交付的产品，不是单纯“做得更好看”

面向有一定文化基础、但在大学日常中缺少接触传统文化机会的学生。每天打开电脑，自然遇到一首与**传统节日 > 当地真实天气 > 节气**相关的诗；无合适内容或天气不可用时诚实降级。默认是低打扰的小诗笺，只显示完整节选、题名作者、一句可信的推荐理由和必要操作；愿意深入时才展开全文、注释、背景、今日联系和可核查出处。重要事件以后走人工策展与审核，不由实时新闻自动决定推荐。

体验原则：**诗是主角，环境是线索，操作随时可找，用户能控制大小和动效**。竖排是可切换的阅读方式，不是缩小空间的硬指标；当它使长诗、词、标题或按钮拥挤时，完整回退横排或适度增高窗口。小、中、大窗口尺寸与正文字号分开控制；每次自动出现仍是小诗笺，主动展开才进入可调整的阅读窗。默认只有轻微动效，允许静态，系统减少动态或窗口隐藏时停止循环装饰。每画面最多一个主意象和一个有含义的小组件，不把未更新天气画成当地正在下雨或下雪。

本任务不以“画满中国风元素”为目标，也不添加背景音乐、自动播放音频、实时抓取热点、未经审核的 AI 诗词解释或新的用户行为追踪。美术资产若不是现有 CSS/SVG，先记录来源、授权范围和体积，再决定是否引入。

## 4. 视觉与使用验收的最小场景矩阵

每个界面批次至少覆盖下面的适用行；需要组合时采用成对覆盖并记录未覆盖组合，不能拿一张“正常诗”截图代表所有状态。逻辑视口用于早期排版，原生 WebView2 证据用于最终签收。

| 场景 | 必须观察的问题 | 不通过示例 |
|---|---|---|
| 普通短诗、默认横排、浅色、小诗笺 | 十秒内是否读到诗句、题名作者和一句理由；继续读/收藏/收起能否立即看见。 | 操作被截在窗外；必须滚动才能知道这首诗是什么。 |
| 长题名、最长节选、最长合法理由 | 窗口是否按工作区增高；增高不足时能否安全滚动并返回。 | 缩小到难读字号、遮按钮、文字横向溢出。 |
| 五言、七言、词、长诗和特殊标点竖排 | 列从右向左、字从上向下；原文不删字；辅助信息仍横排。 | 书名号/数字转向错乱，读屏顺序与视觉顺序不一致。 |
| 节日与天气冲突、节气同日 | 主要推荐理由和主要美术只突出正确的优先情境。 | 节日诗却以不相关雨景为主，理由说天气、画面说节日。 |
| 新鲜雨/雪、缓存天气、离线/未知天气 | 标签、理由、意象是否同源且可信；天气不是诗作标签时是否使用中性画面。 | 缓存或离线时画实时雨雪；诗中春雨被表现为冬季当地雨。 |
| 深色、减少动态、隐藏/最小化 | 文本对比度、焦点、动画停机和恢复后状态。 | 文字因背景不可辨，托盘里仍持续渲染。 |
| 安全预警、内容撤回、资料库失败 | 警示优先于装饰，长说明可读，可恢复/移除路径可达。 | 继续显示普通诗境；资料故障时出现空白首次设置。 |
| 阅读窗、小中大字号、低屏高 | 全文和返回入口可达，调整尺寸不触发新推荐。 | 放大后底部按钮失踪，窗口离开工作区。 |

视觉判断分两层：AI 可证明“未遮挡、层级清晰、文字一致、操作可达、动效受控”；“雅致、不疲劳、愿意每天见到”必须在 H1 由目标用户和项目方看真实窗口后判断。不要用 AI 自己给画面打分代替人测。

## 5. 每个 AI 批次必须执行的自验收循环

1. **先划边界**：读取本文件、原执行方案对应 T 项、体验审查、当前 `review/redesign/Txx`、相关源码与测试；检查 Git 已有改动、运行中的候选、EXE 哈希。明确本次要关闭哪一条 A 节点子项，列出不做的范围。
2. **先设反例**：写出正常、边界、失败至少各一个复现输入和预期。可自动化的缺陷先让针对当前缺陷的测试失败，修复后同一测试通过；纯视觉问题则保留同一场景的修改前后图与观察记录。不能放宽断言或删除失败样本。
3. **小批实现**：沿 Vue 3/TypeScript/Tauri 2 现有栈增量修改；不重建整套 UI。样式按现有暖纸色、宋体阅读、朱砂点缀做有依据的迭代；新增依赖需检查许可、体积与性能。
4. **分层验证**：先跑相关单测，再跑 `npm.cmd run lint`、`npm.cmd run typecheck`、`npm.cmd run test`、`npm.cmd run build`；涉及 Rust 才做对应编译/格式/测试。界面问题再看实际 Windows 窗口；静图不能证明动效，模拟 DOM 不能证明系统焦点和读屏。
5. **记录证据**：在 `review/redesign/` 中记录 commit、候选 EXE 哈希、隔离资料、操作步骤、原始测试结果、可读截图/短录屏路径。若新哈希改变，受影响的原生、性能与安装证据要重做；不改旧发布 `output` 证据来掩盖新版缺项。
6. **逐条签单**：每一条退出条件只写“通过 / 失败 / 未测”，附证据与下一动作。必需子项有失败或未测时，整体只能是“失败/部分通过”，不能写“已完成”。修复后复验，再进入依赖任务。

通用阻断条件：错误城市或不实天气、明显错季推荐；诗句/安全文字/关键按钮不可读或不可达；未经确认丢资料或丢设置；自动抢焦点或全屏打断；内容撤回后继续展示；新增动效在减少动态或隐藏时仍循环；当前候选的性能或发行门禁失败。遇到这些问题先修复或如实暂停，不通过美术微调绕过。

## 6. 验收记录格式与“完成”的含义

每个 T 项保存一份追加式记录，至少包含：`任务与目标行为｜开始时 Git/候选状态｜改动文件及理由｜正常/边界/失败测试与结果｜真实 Windows 环境和操作观察｜视觉样本矩阵｜源码 commit 与 EXE/安装包 SHA-256｜通过/失败/未测逐项判定｜未覆盖风险｜下一步`。如果桌面控制、读屏设备、Windows 10 或真实在线天气暂时不可用，记录“未测”及所需条件，不用自动测试冒充。

“代码已实现”≠“A 节点通过”；“A0–A10 通过”才可称工程改版完成；“A0–A10 + H1 通过”才可称本轮体验验收完成。校园试点与公开发布仍由原项目就绪、签名、法律、安装和试点门禁单独决定。七天长测跳过意味着相关完整门禁继续保持 `partial`。
