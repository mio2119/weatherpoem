# WeatherPoem Windows 代码签名取得与执行计划

更新时间：2026-07-24  
适用基线：WeatherPoem 0.2.0 / `trial` / `unsigned-trial`  
当前结论：组织准备和验收方案已就绪，尚未取得证书或签名服务。

机器计划位于 `review/windows-code-signing-plan.json`，运行
`npm run signing:plan:check` 可确认它仍绑定当前 release 清单、三项发布物、
Tauri 配置和 production 验证实现。

## 当前事实

portable EXE、NSIS 和 MSI 当前均为 `NotSigned`，没有正式 HTTPS 下载地址，
`tauri.conf.json` 也没有证书指纹、时间戳或自定义签名命令。因此它们只能作为
受控内部试用包，不能通过增加说明文字变成正式公开发布物。

正式签名需要项目所属组织作出真实决定，AI 和开发人员不能代替：

- 法律发布主体及证书显示名称；
- 使用组织验证/扩展验证证书、托管签名服务或组织自有签名基础设施；
- 证书/服务预算与合同；
- 私钥托管、恢复、签名权限和审计；
- 可信时间戳服务；
- 允许的签名主体和证书指纹；
- 续期、轮换、吊销和密钥泄露处置。

Tauri 的 Windows 签名说明：
<https://v2.tauri.app/distribute/sign/windows/>。

## 密钥与发布机边界

- 私钥不得进入 Git、客户端、普通开发机或 `D:\纯净工作台`；
- 普通开发人员不能直接签署 production；
- 构建任务最多能请求签名，不能读取或导出私钥；
- production 签名至少需要发布与安全的多人批准；
- 签名服务调用、主体、文件哈希和时间必须进入不可篡改审计日志；
- 签名失败必须让 production 流水线失败，不能自动退化为未签名公开包。

真实选型完成前，不在 `tauri.conf.json` 写虚构指纹、时间戳 URL 或签名命令。

## 正确顺序

1. 在受控 Windows 发布机从批准源码和锁文件构建暂存物；
2. 对主 EXE 以及最终 portable、NSIS、MSI 执行组织签名和可信时间戳；
3. 用 Windows 原生工具验证签名状态、主体、指纹、证书有效期和时间戳；
4. 只对最终签名字节计算尺寸与 SHA-256；
5. 生成 production 清单并执行 `npm run release:verify:production`；
6. 进入公开分发演练，从独立 HTTPS 地址重下后再验证一次。

签名后文件字节会变化，所以不能先生成正式哈希再签名。

## 十个验收场景

计划固定覆盖：

1. 三项发布物全部 `Valid`；
2. 三项均有可信时间戳；
3. 错误主体或指纹；
4. 签名后字节篡改；
5. 任一发布物未签名；
6. 证书过期、吊销或链不受信；
7. 签名后再生成清单；
8. 私钥不可导出与最小权限；
9. 证书续期和允许列表切换；
10. 签名服务不可用。

每个场景必须绑定真实发布物哈希、原生验证输出、执行人、时间和审批证据。浏览器
提示消失、安装成功或文件带有签名图标都不能替代完整验证。

## 通过条件

RQT-19 只有在以下条件全部具备时才能从 `partial` 改为 `passed`：

- 真实发布主体、签名能力、预算和责任人获批；
- 私钥托管、恢复、续期、吊销与审计机制已运行；
- 三项 production 发布物签名均为 `Valid`，具有可信时间戳；
- 主体和指纹属于项目允许列表；
- production 清单基于签名后的最终字节；
- 10 个场景执行完成，P0/P1 为零或有具名风险接受；
- `review/evidence/RQT-19-code-signing-approval.json` 由项目发起人、发布、安全和
  法务责任人签署。
