# WeatherPoem 项目就绪与证据门禁

更新时间：2026-08-05

## 当前结论

项目当前只能声明“未签名内部试用就绪”，不能声明校园试点或公开发布就绪。

| 里程碑 | 已通过 / 必需门禁 | 当前结论 |
| --- | ---: | --- |
| M1 未签名内部试用 | 7 / 7 | `ready` |
| 30—50 人校园试点 | 7 / 18 | `not-ready`，11 个阻断项 |
| 正式公开发布 | 7 / 24 | `not-ready`，17 个阻断项 |

24 项门禁当前分布为：

- `passed`：7；
- `partial`：16；
- `pending`：1；
- `blocked`：0；
- `failed`：0。

权威定义保存在 `review/requirements-traceability.json`，稳定生成结果保存在
`output/WeatherPoem_0.2.0_READINESS.json`。生成结果会同时读取当前应用版本、
内容目录、试用发布清单、设备矩阵和人工 Windows 证据是否存在。

## 三层证据不能互相替代

1. **工程自动证据**：代码、测试、内容目录、哈希、安装包和机器报告。  
   它能证明实现与当前二进制，但不能替代专家、授权、试点或组织签署。
2. **人工设备证据**：具名设备矩阵、管理员 MSI、真实重启、自助安装、性能、
   辅助技术和演练记录。  
   浏览器尺寸检查或脚本存在都不能自动替代真实执行。
3. **外部责任证据**：内容专家、数据授权、隐私同意、预算、签名证书、试点结果
   和 Go/No-Go。  
   AI 只能准备模板、校验结构和发现矛盾，不能代替真实责任人签字。

因此，“单元测试全部通过”“能生成安装包”或“本机没有发现问题”都不足以把
校园试点或公开发布改成 `ready`。

## 使用命令

更新追踪表或证据后重新生成：

```powershell
cd E:\weatherpoem
npm run requirements:generate
npm run requirements:check
```

检查校园试点门禁：

```powershell
npm run requirements:pilot
```

检查正式公开发布门禁：

```powershell
npm run requirements:public
```

后两个命令在任何必需项不是 `passed` 时都会退出失败，并逐项输出责任角色和
下一步。当前 `requirements:pilot` 按预期拒绝通过，列出 11 个阻断项。只有
追踪表先证明里程碑就绪后，命令才会继续执行全量 `npm run check`；校园试点还会
执行管理员 Windows 人工证据门禁，公开发布还会执行 production 签名门禁。

`npm run check` 已包含 `requirements:check`，所以追踪表版本不一致、已通过证据
被删除、设备矩阵被冒充、未签名包被写成正式签名版，都会使普通工程检查失败。

## 人工证据规则

人工或外部工作完成后，按 `review/evidence/README.md` 创建具名摘要。门禁会
拒绝：

- 匿名或 `TBD`、“待定”等占位执行人；
- 没有批准人、执行时间或检查时间；
- 未绑定当前应用版本和内容版本；
- 空证据列表；
- 含凭据的 URL；
- 指向不存在仓库文件的相对路径；
- 未来时间；
- 仅有文件但专用机器门禁仍不通过的结论。

原始合同、密钥、个人敏感信息和完整第三方响应不得写入仓库。证据摘要可以引用
组织批准的无凭据 HTTPS 工单或审批页面。
