# WeatherPoem 规范许可文本补充与双层覆盖设计

日期：2026-07-24  
状态：待用户复核  
适用版本：WeatherPoem 0.2.0 内部受控试用候选

## 1. 背景

当前第三方 NOTICE 流程只接受以下两类可读文本：

1. 锁定的 npm 包、crate 或其发布归档实际携带的许可、版权、NOTICE 文件；
2. 能由 npm `gitHead` 或 crate `.cargo_vcs_info.json` 绑定到固定提交的上游仓库许可文件。

这套规则已经覆盖绝大多数依赖，但仍有 11 个锁定依赖没有可按上述规则取得的许可全文：

- npm：
  `@humanfs/types@0.15.0`、`@tybys/wasm-util@0.10.3`、
  `boolbase@1.0.0`、`eastasianwidth@0.2.0`、`esrecurse@4.3.0`、
  `imurmurhash@0.1.4`、`keyv@4.5.4`、`natural-compare@1.4.0`、
  `stackback@0.0.2`；
- Cargo：`crc-catalog@2.5.0`、`selectors@0.36.1`。

同步器已经按锁文件校验并检查过这些发布归档。部分包有固定 `gitHead`，但对应提交没有根级许可文件；部分旧包没有 `gitHead` 或可证明与发布归档一致的版本标签；另有工作区包只在相邻目录携带许可文件。不能为了让覆盖率变成 100% 而把不确定的父仓库、当前分支或相似包文件冒充为该发布包的随包许可文本。

## 2. 目标

在不改变“上游随包文本覆盖率”含义的前提下，为分发 NOTICE 提供可复现、可校验、明确标注来源性质的规范许可全文补充。

具体目标：

1. 上游文本覆盖率继续如实保留 11 个缺口，不因补充规范文本而被改写；
2. 分发可读许可文本覆盖率在所有受控例外通过校验后达到 100%；
3. 规范文本必须来自 SPDX 官方 `license-list-data` 的固定发布和固定提交；
4. 每个补充项必须同时绑定当前依赖名称、版本、许可表达式、包来源及锁文件完整性字段；
5. NOTICE 必须明确说明这是规范许可文本补充，不是上游发布包携带的文件；
6. 任何未知许可、表达式不匹配、来源漂移、内容篡改或新增未审批缺口都必须让生成或检查失败；
7. 该机制不宣称依赖许可兼容、项目发布许可已经确定或已经获得法律批准。

## 3. 方案选择

采用“显式例外策略 + 固定 SPDX 发布 + 双层覆盖报告”的方案。

未采用的方案：

- 保持 11 个缺口不处理：最严格，但最终安装包中的 NOTICE 仍缺少这些包所声明许可的可读全文；
- 逐包猜测父仓库、兄弟包或旧版本标签：来源关系不统一，部分包无法把猜测的提交与 npm/crate 发布归档可靠绑定；
- 静默使用通用模板并把原覆盖率改成 100%：会把“上游实际携带”与“分发侧补充”混为一谈，证据含义不诚实；
- 从 SPDX 默认分支实时读取：来源会随上游变化，无法复现已发布 NOTICE。

## 4. 固定规范文本来源

规范文本唯一允许的来源为：

- 仓库：`https://github.com/spdx/license-list-data`
- 稳定发布：`v3.28.0`
- 固定提交：`c4a7237ec8f4654e867546f9f409749300f1bf4c`
- 允许的文件：
  - `text/Apache-2.0.txt`
  - `text/BSD-2-Clause.txt`
  - `text/ISC.txt`
  - `text/MIT.txt`
  - `text/MPL-2.0.txt`

下载命令必须使用含上述完整提交 SHA 的 GitHub Contents API URL。发布标签仅用于说明来源版本；安全边界由固定提交、下载响应 SHA-256、落盘字节数和落盘 SHA-256 共同建立。

## 5. 数据与文件设计

### 5.1 人工审查策略

新增：

`review/canonical-license-text-policy.json`

该文件是人工可审查的例外白名单，不由 NOTICE 生成器自动扩张。至少包含：

- Schema 版本；
- SPDX 仓库、发布标签和固定提交；
- 允许的 SPDX 许可标识；
- 11 个包的生态、包 ID、名称、版本、当前许可表达式；
- npm 的 `resolved`、`integrity`，或 Cargo 的 `source`、`checksum`；
- 选择规范文本补充的原因代码 `upstream-readable-text-unavailable`；
- 对复合表达式 `MIT OR Apache-2.0` 明确列出两个许可标识。

当前报告出现新的上游文本缺口时，命令不得自动加入白名单，必须失败并要求人工审查。

### 5.2 同步证据清单

新增：

`review/canonical-license-text-supplements.json`

同步命令根据策略文件下载固定提交中的五份文本，并生成证据清单。每份文本至少记录：

- SPDX 许可标识；
- SPDX 发布标签和固定提交；
- 仓库相对路径；
- 含完整提交 SHA 的来源 URL；
- 本地相对路径；
- 字节数和 SHA-256。

每个包的绑定记录同时复制并校验策略中的身份字段，避免旧版本策略被应用到新锁文件。

### 5.3 本地只读来源

规范文本保存到：

`third_party/license-texts/spdx/v3.28.0/`

NOTICE 生成与离线检查只读取这些已锁定文件，不在普通生成阶段访问网络。只有显式同步命令可以访问 SPDX 上游。

## 6. 处理流程

新增显式同步命令：

`npm run licenses:notices:sync:spdx`

流程如下：

1. 读取当前 npm/Cargo 锁文件、当前第三方 NOTICE 索引和人工策略；
2. 校验策略恰好覆盖当前 11 个上游文本缺口，既不遗漏也不包含已有上游可读文本的包；
3. 校验每个包的名称、版本、许可表达式、来源和完整性字段与当前项目一致；
4. 只从固定 SPDX 提交下载策略允许的许可文本；
5. 严格 UTF-8 解码，拒绝空文件、NUL、替换字符和未列出的路径；
6. 写入规范文本文件；
7. 生成同步证据清单并记录字节数与 SHA-256；
8. 后续 NOTICE 生成只消费策略、证据清单和本地规范文本。

普通 `licenses:notices:generate` 不得隐式联网，也不得更新策略。

## 7. 双层覆盖语义

报告同时给出两套不可互相替代的指标。

### 7.1 上游可读文本覆盖

只计算发布归档、固定上游提交以及现有“同发布平台包/同工作区包”映射提供的可读文本。

保留现有字段语义：

- `packagesWithoutReadableNoticeText`
- `readableTextCoveragePercent`
- `missingTextPackageIds`

应用规范文本补充后，这组指标仍如实列出 11 个缺口。

### 7.2 分发可读许可覆盖

在上游文本基础上，再计算通过全部校验的 SPDX 规范文本补充。

新增字段：

- `packagesWithoutDistributionLicenseText`
- `distributionLicenseTextCoveragePercent`
- `missingDistributionLicenseTextPackageIds`
- `canonicalFallbackPackageCount`

只有 11 个白名单包全部通过身份和内容校验时，分发覆盖率才可达到 100%，缺失列表才为空。

字段名称不得使用 `legalComplete`、`licenseApproved`、`compliant` 或含义相同的表达。

## 8. NOTICE 呈现

规范文本按 SPDX 许可标识分组，避免把相同全文为每个包重复一次。每个分组必须列出：

- SPDX 许可标识；
- 适用的包 ID、名称和版本；
- “上游发布包未提供可验证的可读许可全文，本节由分发侧补充 SPDX 规范文本”的明确说明；
- SPDX 发布标签、固定提交和本地证据清单路径；
- 完整规范许可文本。

复合表达式 `MIT OR Apache-2.0` 的包同时出现在 MIT 与 Apache-2.0 分组中，并保留原始 `OR` 语义；生成器不得擅自替项目选择其中一种许可。

报告中的每个规范文本文件使用独立来源类型：

`verified-spdx-canonical-text`

该来源类型不得被现有的 `verified-npm-archive`、
`verified-npm-git-commit` 或 `verified-cargo-git-commit` 代替。

## 9. 校验与失败规则

以下任一情况必须失败，且不得生成看似完整的新 NOTICE：

- 策略 Schema、证据清单 Schema 或固定 SPDX 身份不匹配；
- 策略缺少当前上游文本缺口，或包含不再缺失的包；
- 包名、版本、许可表达式、来源、完整性值与锁文件不一致；
- 许可表达式不能无歧义地映射到策略列出的 SPDX 标识；
- `OR` 表达式缺少任一备选许可全文；
- 来源 URL 未固定到允许的完整提交 SHA；
- 本地路径越出 `third_party/license-texts/spdx/v3.28.0/`；
- 文件缺失、为空、不是严格 UTF-8，或字节数、SHA-256 不一致；
- 同一包或同一许可标识重复、存在未知字段或未授权的额外文件；
- 新增依赖产生新的上游文本缺口但尚未进入人工策略。

失败信息必须指出包 ID 或许可标识以及不匹配字段，不输出用户主目录等无关绝对路径。

## 10. 测试策略

严格按测试驱动开发执行。

先写并运行失败测试，至少覆盖：

1. 合法的单许可包可以附加规范文本但不改变上游覆盖率；
2. `MIT OR Apache-2.0` 同时附加两份文本并保留 `OR`；
3. 分发覆盖率与上游覆盖率分别计算；
4. 新缺口未进入策略时失败；
5. 策略包含已有上游文本的包时失败；
6. 包版本、许可表达式、来源或完整性字段被交换时失败；
7. SPDX 仓库、标签、提交、路径或 URL 不符合固定身份时失败；
8. 文件缺失、哈希篡改、字节数不符或 UTF-8 无效时失败；
9. 路径越界、重复项、未知许可标识和不完整 `OR` 映射时失败；
10. 生成的 NOTICE 明确标注规范补充，且不会写出法律完成声明；
11. 既有归档、Git 提交和同发布映射来源仍按原规则工作。

每个测试必须先因缺少新行为而出现预期失败，再实现最小逻辑使其通过，最后运行完整许可和项目检查。

## 11. 文档与追踪更新

实现通过后更新：

- `docs/CONTENT_ASSET_LICENSES.md`
- `docs/MVP_VERIFICATION.md`
- `docs/WeatherPoem_产品设计工作稿.md`
- RQT-23 追踪证据

文档必须同时给出上游覆盖与分发覆盖，不得只展示 100% 分发覆盖而隐藏 11 个上游缺口。

即使分发可读许可覆盖达到 100%，RQT-23 仍保持“部分完成”，直至项目自身发布许可确定、必要的许可兼容性判断完成并获得具名法律复核。

## 12. 验收标准

机器验收：

- 人工策略恰好绑定当前 11 个上游文本缺口；
- 五份 SPDX 文本来自 `v3.28.0` 的固定提交且通过字节/哈希校验；
- 上游覆盖指标仍保留 11 个缺口；
- 分发可读许可文本覆盖率为 100%，分发缺失列表为空；
- NOTICE 明确区分上游文本与规范补充，并完整包含五种许可文本；
- 所有新增测试经历可观察的红、绿阶段；
- 完整许可检查、完整项目检查和普通发布验证通过；
- 文档不把工程覆盖结果表述为法律批准。

人工验收：

- 审阅 11 个例外是否确为当前锁定依赖；
- 审阅 NOTICE 中的规范补充说明是否足够醒目；
- 法务后续决定这些补充是否满足最终公开分发要求。

本设计只关闭“分发 NOTICE 缺少可读许可正文”这一工程子项，不关闭项目发布许可与法律复核事项。
