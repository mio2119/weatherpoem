# WeatherPoem 人工策展重要事件专题设计

## 1. 设计目的

WeatherPoem 的原始愿景不仅包括节日、天气和节气，也包括把正在发生的重要事件与传统文化连接起来。首版需求为了控制时效、立场、来源和审核风险，排除了实时新闻，但尚未说明这项愿景如何在后续版本中落地。

本设计采用“人工策展的重要事件专题”，保留重要事件能力，同时避免把未经审核的实时热点直接送入开机自动推送。

## 2. 核心决策

1. MVP 与四周校园试点不接入实时新闻源，也不自动抓取社会热点。
2. 校园试点完成并通过 Go/No-Go 后，才允许启用人工策展的重要事件专题。
3. 专题仅面向事实已经稳定、与传统文化存在自然连接、适合大学生日常理解的文化、纪念、教育和公共知识事件。
4. 每个专题必须由具名编辑提交、具名审核人批准，并设置开始时间、结束时间和撤回条件。
5. AI 不读取原始新闻，也不决定某个事件是否值得推送。AI 只能在人工批准的诗词候选集合中排序，并生成受约束的简短推荐理由。
6. 主卡片仍只展示一首诗，不因事件专题增加主空间的信息密度。

## 3. 方案比较

### 方案 A：自动接入实时新闻

优点是覆盖快、事件多；缺点是来源、事实、立场、隐私、灾害表达和审核成本不可控，不适合每日自动触达的桌面产品。

### 方案 B：人工策展少量专题

优点是保留“当下性”，同时能够锁定来源、候选诗词、表达口径、有效期和撤回路径；缺点是需要编辑与审核资源，无法覆盖所有热点。

### 方案 C：永久只做节日、天气和节气

优点是最稳定；缺点是放弃了产品将传统文化连接到现实公共生活的长期价值。

采用方案 B。

## 4. 事件准入边界

### 4.1 可以进入专题的事件

- 已由权威机构或多个可靠来源确认、核心事实稳定的文化事件。
- 重要文化遗产、考古、典籍、艺术和教育成果的正式发布。
- 具有明确公共纪念意义、且能以克制方式连接传统文化的纪念日或纪念活动。
- 与大学校园生活、公共文化生活有关，且不会要求用户持有特定立场的公共知识事件。

### 4.2 不得进入专题的事件

- 正在快速变化的突发新闻、未经证实的网络热点和自媒体传闻。
- 灾害、事故、伤亡、战争或公共安全事件的诗意化表达。
- 需要即时政治立场判断、可能造成群体伤害或存在明显争议的事件。
- 商业营销、品牌公关、明星娱乐、榜单和流量话题。
- 无法提供可定位来源、有效期和具名审核记录的事件。

严重天气预警或公共安全风险存在时，仍以安全信息为先，暂停普通诗笺和重要事件专题。

## 5. 推荐优先级

普通日推荐优先级继续保持：

`节日 ＞ 天气 ＞ 节气`

只有已经人工批准、处于有效期内且没有安全抑制条件的专题，才使用：

`人工批准的重要事件专题 ＞ 节日 ＞ 天气 ＞ 节气`

重要事件不是新的常驻自动数据源，而是一种稀少、带发布决策的编辑覆盖层。没有有效专题时，系统行为与现有推荐逻辑完全一致。

## 6. 数据模型

每个事件专题至少包含：

| 字段 | 必填 | 说明 |
|---|---|---|
| `event_id` | 是 | 稳定且不可复用的专题标识 |
| `title` | 是 | 中性、事实性的专题名称 |
| `event_type` | 是 | 文化、纪念、教育或公共知识 |
| `summary` | 是 | 不超过 120 字的事实摘要 |
| `cultural_connection` | 是 | 与传统文化连接的编辑说明 |
| `source_records` | 是 | 可定位的权威来源、标题和访问日期 |
| `region_scope` | 是 | 全国、地区或城市；不得暗示不适用地区 |
| `starts_at` | 是 | 专题开始生效时间 |
| `expires_at` | 是 | 专题自动失效时间 |
| `candidate_poem_ids` | 是 | 已审核诗词候选，至少 2 首 |
| `fallback_reason` | 是 | AI 不可用时的人工推荐理由 |
| `risk_level` | 是 | 低或中；高风险事件不得发布 |
| `editor_name` | 是 | 真实编辑人员 |
| `reviewer_name` | 是 | 与编辑不同的真实审核人员 |
| `approved_at` | 是 | 审核通过时间 |
| `withdrawal_reason` | 否 | 撤回时必填 |
| `status` | 是 | 草稿、待审核、已批准、已发布、已过期或已撤回 |

所有时间使用带时区的 ISO 8601。专题到期后必须自动退出候选，不能依赖人工记忆下线。

## 7. 编辑与发布流程

1. 编辑创建专题，填写事实摘要、文化连接、来源、地域、时效和候选诗词。
2. 系统自动检查字段完整性、时间范围、候选作品状态和来源可定位性。
3. 与编辑不同的审核人检查事实、表达、安全边界、地域适用性和诗词连接。
4. 审核人批准后，专题才可进入待发布队列。
5. 发布任务在 `starts_at` 生效，在 `expires_at` 自动失效。
6. 来源变化、事实更正或表达风险出现时，编辑可立即撤回；客户端下一次同步后不再展示。
7. 发布、修改、撤回和过期都保留审计记录。

不允许跳过审核直接发布，也不允许 AI 自动生成并发布事件专题。

## 8. 客户端体验

### 8.1 主卡片

- 仍只显示一首诗、作者篇名、一句诗和 40 字以内的推荐理由。
- 仅增加一个低显著度的“今日专题”标签，不堆叠新闻标题、来源列表或事件长摘要。
- 不增加声音、抢焦点、重复弹出和额外通知。

### 8.2 扩展阅读

用户点击“了解更多”后，扩展阅读增加：

1. “为什么是今天”：事件与作品的连接。
2. “事件背景”：克制的事实摘要。
3. “可靠来源”：可定位的来源列表。
4. 原有的完整诗文、出处、文化背景、注释和当代连接。

事件背景默认折叠；主卡片和扩展阅读都不能变成新闻客户端。

## 9. AI 边界

AI 输入只能包含：

- 已批准专题的结构化字段。
- 已批准的候选诗词事实和标签。
- 当前城市、日期以及现有安全情境。

AI 输出只能包含：

- 一个候选作品 ID。
- 一段不超过 40 字的推荐理由。

输出必须再次校验作品 ID、事实引用、长度和敏感表达。AI 失败、超时或输出不合格时，使用人工 `fallback_reason`；不得临时抓取网络内容补全。

## 10. 失败与安全处理

- 专题服务不可用：忽略专题，回到节日、天气、节气逻辑。
- 专题过期或状态异常：拒绝使用并记录诊断，不延长有效期。
- 客户端内容版本不兼容：忽略专题，不影响离线诗笺。
- 严重天气或公共安全抑制：暂停专题和普通诗笺。
- 来源撤回或事实更正：专题立即撤回；已缓存副本不得继续展示。
- 没有合格候选诗词：专题不得发布，不由 AI 临时选诗。

## 11. 隐私与统计

- 不收集用户阅读的具体事件标题、政治倾向或立场推断。
- 沿用现有可选匿名统计，只记录专题送达、展开、不感兴趣和故障的按日聚合。
- 用户关闭匿名统计后，不发送任何专题行为事件。
- 事件专题不新增定位权限，仍只使用用户手动确认的城市级地域。

## 12. 上线门禁

启用重要事件专题前必须满足：

1. 四周校园试点完成并形成 Go/No-Go。
2. 具名内容编辑、内容审核和安全责任人已经确定。
3. 来源、双人审核、自动过期、撤回和客户端缓存防回退均完成验证。
4. 至少 10 个历史事件样本通过编辑演练，且包含到期、撤回、地域不适用和 AI 失败场景。
5. 严重天气与公共安全抑制测试全部通过。
6. 非开发人员 UAT 确认主卡片没有增加明显信息负担。

## 13. 验收标准

- 未经批准的专题进入推荐候选次数为 0。
- 已过期或已撤回专题继续展示次数为 0。
- 每个已发布专题都有两个不同的具名人员和可定位来源。
- 主卡片仍只展示一首诗，自动出现频率仍为每自然日最多一次。
- 事件专题服务失败时，节日、天气、节气推荐仍可正常工作。
- 严重天气和公共安全抑制条件下，专题展示次数为 0。
- 用户对专题选择“不感兴趣”后，当日不再展示该专题。
- 试运行中“与今天不相关”反馈低于 10%，且没有已确认的事实或安全错误。

## 14. 版本安排

- `0.2–1.0`：保持现有范围，不接实时新闻和重要事件自动推荐。
- `1.1 Decision`：根据四周试点证据决定是否投入编辑与审核资源。
- `1.2 Curated Context`：门禁满足后，小范围启用人工策展的重要事件专题。

本设计不授权实时新闻抓取、自动热点判断、灾害诗意化、无审核发布或面向全量用户立即开启。
