# WeatherPoem 七天稳定性证据管线设计

日期：2026-08-05  
状态：待用户书面复核  
适用候选：WeatherPoem 0.2.0，当前冻结 EXE

## 1. 目标

为当前冻结的 WeatherPoem 候选增加一条可复算、可恢复核验、不会覆盖八小时证据的七天连续托盘稳定性管线。正式运行必须持续至少 10,080 分钟，每分钟采样一次，报告绑定启动时的 EXE 版本、大小和 SHA-256，并证明应用在受控离线诗笺场景中始终存活、CPU 和内存满足既有阈值。

这条管线只关闭 `RQT-13` 中的“七天连续运行”子项。它不自动声明休眠/唤醒、真实天气、真实 AI、官方预警、内容更新、事件积压或具名质量签署已经完成，因此完整 `RQT-13` 继续保持 `partial`。

## 2. 方案选择

考虑过三种方案：

1. 直接把现有八小时脚本的时长改为七天。改动少，但会继续写入八小时报告和通用检查点，容易覆盖已经通过的正式证据，不能采用。
2. 新增独立七天入口，并复用经过验证的底层采样逻辑。七天启动清单、检查点、正式报告、状态和校验器各自独立；现有八小时命令保持兼容。这是本设计采用的方案。
3. 只用人工表格记录七天观察。能补充体验信息，但无法复算资源数据、进程连续性和候选哈希，不能作为主要工程证据。

## 3. 范围与非目标

本次包括：

- `performance:seven-day:start`：后台启动正式七天测量；
- `performance:seven-day:status`：只读查看启动清单、检查点、进程和进度；
- `performance:seven-day:check`：独立复算七天正式报告；
- 七天模式的契约测试、状态测试、启动脚本安全测试；
- 性能说明和需求追踪文字更新；
- 启动前验证冻结 EXE 哈希，并在运行期间禁止重建候选。

本次不包括：

- 自动让 Windows 睡眠、唤醒或重启；
- 模拟休眠来冒充真实电源状态变化；
- 调用真实天气、AI 或预警生产服务；
- 修改候选 EXE、NSIS 或 MSI；
- 把七天自动报告冒充具名质量签署；
- 把 `RQT-13` 或校园试点里程碑改为 `passed`。

## 4. 文件和命令隔离

八小时现有文件保持原样：

- `output/WeatherPoem_0.2.0_PERFORMANCE_8H_LAUNCH.json`
- `output/WeatherPoem_0.2.0_PERFORMANCE_LONG_RUN_CHECKPOINT.json`
- `output/WeatherPoem_0.2.0_PERFORMANCE_8H.json`

七天模式只写入：

- `output/WeatherPoem_0.2.0_PERFORMANCE_7D_LAUNCH.json`
- `output/WeatherPoem_0.2.0_PERFORMANCE_7D_CHECKPOINT.json`
- `output/WeatherPoem_0.2.0_PERFORMANCE_7D.json`
- `output/performance-7d-archive/` 下的同模式历史归档

任何七天命令都不得删除、改名、归档或覆盖八小时文件。启动器不得执行构建、打包、安装或签名命令。

## 5. 采样器设计

现有 `scripts/test-performance-long-run.ps1` 保留默认八小时行为，并增加显式证据模式。调用方只有指定 `seven-day` 模式时才能请求 10,080 分钟；八小时模式继续拒绝超过 1,440 分钟的运行，演练模式继续限制在 30 分钟以内。

七天正式模式使用以下固定配置：

- 时长：10,080 分钟；
- 采样间隔：60 秒；
- 场景：受控的 `weather-offline`；
- 数据目录：系统临时目录下的独立性能账户；
- 用户真实数据：不得读取或修改；
- 启动视图：诗笺；
- 主窗口关闭到托盘后开始持续采样；
- CPU 平均值 `< 0.2%`；
- 内存 P95 `< 100 MiB`；
- 首尾内存增长 `< 20 MiB`。

正式报告使用：

- `testKind = performance-seven-day`
- `configuration.mode = seven-day`
- `result = automated-seven-day-passed` 或 `automated-seven-day-failed`
- `limitations.eightHourIdleMeasured = true`
- `limitations.sevenDayLongRunMeasured = true`
- `limitations.sleepWakeMeasured = false`
- `limitations.realNetworkMeasured = false`
- `limitations.namedQualitySignoff = false`
- `gateSatisfied = false`

采样器只终止自己启动且仍持有对象引用的进程。清理仅限解析到系统临时目录、名称带固定性能前缀的本次运行目录。

## 6. 连续性判定

七天校验不能只看报告里的布尔值，必须从所有样本独立复算：

- 实际墙钟时长不少于 604,800 秒；
- 样本数不少于 10,080；
- `elapsedSeconds` 与 `recordedAt` 严格递增；
- 相邻样本的墙钟间隔不得超过 150 秒；
- 报告至少跨越七个不同的 UTC 日期；
- 进程始终存活且关闭主窗口后保持托盘运行；
- CPU、内存 P95 和内存增长结论与原始样本一致；
- 报告的 EXE SHA-256、大小和版本与当前冻结候选一致。

超过 150 秒的采样空洞会使“连续七天”失败。真实休眠/唤醒应由独立人工流程记录，不能通过放宽连续性阈值混入本报告。

## 7. 启动、状态与恢复核验

启动器执行以下只读前置检查：

1. 当前 EXE 存在，SHA-256 与启动清单记录一致；
2. 没有 WeatherPoem 进程；
3. 没有仍在运行的七天启动器；
4. 上一轮七天文件如果存在，只能归档到七天专属目录；
5. 八小时三份证据在启动前后哈希完全不变。

启动器随后以隐藏窗口运行采样器，记录 `runId`、启动器 PID、应用候选哈希、固定配置和启动时间。状态命令优先读取当前七天检查点；若检查点被其他演练污染或缺失，只能在七天正式报告通过完整身份、时长、样本和哈希校验后返回 `completed`。它不得把八小时或演练报告当作七天完成证据。

状态输出包括：

- `status`：`starting`、`running`、`completed` 或 `failed`；
- `source`：`checkpoint` 或 `formal-report`；
- `runId`；
- 当前 EXE 哈希；
- 启动器和应用进程是否存活；
- 样本数与进度百分比；
- 最后采样时间；
- 正式报告路径（如已生成）。

## 8. 失败处理

- EXE 哈希在启动前不匹配：拒绝启动，不改任何证据；
- 检测到已有 WeatherPoem：拒绝启动，不终止未知进程；
- 应用中途退出：检查点写为 `failed`，保留诊断信息；
- CPU 或内存超阈值：生成失败报告并使校验命令退出非零；
- 启动器异常退出但应用仍存活：状态命令报告不一致，不自动杀进程；
- 候选在测量期间被替换：最终哈希绑定失败，报告不得通过；
- 机器休眠造成采样空洞：连续性校验失败，同时保留原始检查点，不冒充休眠/唤醒通过。

## 9. 测试策略

实现按失败测试先行：

1. 七天契约接受一份绑定当前候选、10,080 个连续样本的有效报告；
2. 拒绝不足七天、少样本、旧哈希、错误模式和伪造统计值；
3. 拒绝超过 150 秒的采样空洞；
4. 拒绝把 `sleepWakeMeasured`、`realNetworkMeasured` 或 `namedQualitySignoff` 改成 `true`；
5. 状态命令只接受七天检查点或七天正式报告；
6. 启动脚本使用七天专属路径，且不含构建、打包、安装或八小时文件写入；
7. 现有八小时和演练契约继续全部通过；
8. `npm run check`、`performance:eight-hour:check` 和 `release:verify` 继续通过；
9. 最后重新计算 EXE 与八小时三份证据哈希，证明七天工具实现未改变冻结候选或既有正式证据。

为了让单元测试快速完成，契约测试使用合成样本验证复算逻辑；这只验证校验器，不能替代随后真实运行的 168 小时测量。

## 10. 启动后的运行纪律

真实七天测量开始后：

- 不重建、不替换、不签名当前 EXE；
- 不并行运行会启动 WeatherPoem 的单实例、窗口位置、性能或安装生命周期测试；
- 可并行执行不启动应用且不修改候选的只读检查；
- 定期只读执行 `performance:seven-day:status`；
- 完成后先执行 `performance:seven-day:check`，再更新需求追踪和派生文档；
- 即使七天报告通过，仍保留休眠/唤醒、真实在线服务、内容/事件恢复和具名质量签署为未完成。

## 11. 验收标准

工具实现阶段完成的标准：

- 新命令、报告契约和状态契约均有先失败后通过的测试；
- 七天文件与八小时文件完全隔离；
- 全量工程检查、八小时正式校验和发布校验通过；
- 当前 EXE SHA-256 仍为 `D388D9484A7B81B1039CFAA1D21CBAD178750E5375B8FBCA7D8334A8C681609A`。

七天证据阶段完成的标准：

- 正式运行自然结束；
- 10,080 个以上一分钟样本覆盖至少 604,800 秒；
- 连续性、CPU、内存和进程存活全部通过独立复算；
- 正式报告绑定上述冻结 EXE；
- 检查点与应用进程均处于自然完成状态；
- 需求追踪只把“七天连续运行”子项记为已测，不扩大到完整 `RQT-13`。
